## План виправлення

Ви праві: поточна реалізація не доведена до потрібного стану. Я виправлю саме те, що ви просили: рахунок постачальника має бути в адмін-панелі біля кожного магазину, тестові оплати мають реально показуватись, а перемикання ролей через «жука» має змінювати вигляд і доступи.

## Що буде зроблено

### 1. Прибрати рахунок постачальника з профілю
- Видалити кнопку «Рахунок постачальника» з профілю.
- Залишити шлях до рахунку через:
  - адмін-панель → магазини → кнопка «Рахунок» біля кожного магазину;
  - «Керування магазинами» для реального постачальника/менеджера, якщо це потрібно для їх робочого сценарію.

### 2. Рахунок постачальника прямо з адмін-панелі біля кожного магазину
- У блоці магазинів адміна зробити кнопку «Рахунок» зрозумілою, з текстом, не лише іконкою.
- При відкритті `/supplier-balance/:id` рахунок одразу має показувати дані вибраного магазину, а не чекати додаткового вибору.
- Для адміна це повний режим перегляду/керування коштами магазину.

### 3. Виправити «жука», щоб ролі реально змінювали рахунок
- Передавати `preview_role` у всі дії рахунку, включно з історією рухів, статистикою, балансом і списком оплат.
- На бекенді дозволити `preview_role` тільки для реального адміна, але з пониженням доступу:
  - `supplier` → бачить рахунок як постачальник: баланс, історія, ручний вивід, автооплати;
  - `shop_manager` → бачить тільки статуси оплат замовлень, без сум балансу, виплат, карток, IBAN і руху коштів;
  - `moderator` → перегляд фінансових станів без керування коштами;
  - `customer/guest` → без доступу до рахунку.
- Оновити текст у «жуку», бо зараз він сам пише, що це тільки UI, через що очікування не збігається з реальністю.

### 4. Реальні тестові дані для всіх тестових магазинів
- Поточна база має 4 магазини, але не всі мають тестові оплати: `Toy World` взагалі без splits/рухів, `payout_methods` порожній.
- Переробити генератор тестових оплат так, щоб для кожного тестового магазину створювались:
  - тестові замовлення;
  - `order_splits` зі статусами `created`, `processing`, `paid`;
  - рухи коштів: нарахування, наша націнка по наложеному, вивід, повернення/коригування;
  - баланс магазину;
  - тестовий спосіб виплати/картка;
  - дані для менеджерського перегляду оплат.
- Додати в адмін-панель кнопку «Оновити тестові оплати» так, щоб після натискання одразу було видно результат.

### 5. Правильний вигляд для трьох ролей

```text
Адмін:
Адмін-панель → Магазини → Рахунок біля кожного магазину
Бачить баланс, рух коштів, виплати, автооплати, тестові оплати, керування.

Постачальник:
Керування магазинами → Баланс/Рахунок магазину
Бачить свої кошти, історію, ручний вивід, автооплати, картку/IBAN.

Менеджер магазину:
Керування магазинами → Оплати магазину
Бачить тільки статуси оплат замовлень: Створено / Часткова / Оплачено.
Не бачить баланс, рух коштів, картку, IBAN, кнопки виводу або автооплат.
```

### 6. Автооплати зробити окремим правильним екраном/діалогом
- Залишити окрему кнопку «Автооплати» у рахунку постачальника тільки для власника/адміна.
- У діалозі показати і зробити робочими:
  - авто-вивід доступного балансу;
  - мінімальну суму виводу;
  - авто-списання нашої націнки з прив’язаної картки по наложених;
  - поточну прив’язану картку/IBAN;
  - sandbox/live стан Mono/LiqPay.
- Менеджеру цей діалог не показувати взагалі.

### 7. Перевірка після реалізації
- Перевірити дані в базі: кожен тестовий магазин має баланс, рухи, splits і спосіб виплати.
- Перевірити в preview:
  - адмін відкриває адмін-панель → магазини → рахунок конкретного магазину;
  - «жук» → supplier: показує фінансовий рахунок і автооплати;
  - «жук» → shop_manager: показує лише статуси оплат;
  - «жук» → moderator: показує тільки перегляд без керування;
  - профіль більше не містить окремого меню рахунку постачальника.
