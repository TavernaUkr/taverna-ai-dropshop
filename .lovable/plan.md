# Панель оплат (Payments / Payouts Panel)

Автоматизована система виплат постачальникам із трьома статусами, контролем модератора, оглядом для постачальників і повним керуванням для адміна. Виплати запускаються після підтвердження доставки через Нову Пошту та з урахуванням 14-денного вікна обміну/повернення.

## Модель статусів (для кожного «куска» замовлення = order_split)

```text
СТВОРЕНО      Клієнт оформив замовлення. Кошти за товар(и) постачальника
(created)     зафіксовано. Тип оплати:
                • Повна предоплата → тримаємо повну суму
                • Часткова (наша націнка) → решта = наложений на пошті

В ОБРОБЦІ     Клієнт ОТРИМАВ товар (через трекінг Нової Пошти) і минув строк
(processing)  обміну/повернення (0 днів якщо товар незворотний, 14 днів якщо
              зворотний). Бот рахує дропову/оптову суму до перерахування.

ОПЛАЧЕНО      Різницю перераховано постачальнику на його реквізити. До кожного
(paid)        куска прикріплено банківський чек ФОП (авто-запис + ручне фото/PDF).
```

## Частина 1 — База даних (міграція)

**`order_splits` (розширення):**
- `payout_stage` text default `'created'` — `created | processing | paid`
- `payout_type` text — `full_prepaid | partial_markup` (визначається з `payment_method`)
- `eligible_payout_at` timestamptz — коли можна виплачувати (отримання + вікно повернення)
- `receipt_url` text — посилання на чек у сторейджі
- `receipt_uploaded_at`, `paid_at` timestamptz
- `is_returnable` boolean — знімок зворотності на момент виплати

**`products` (розширення):**
- `is_returnable` boolean default true — чи підлягає обміну/поверненню
- `return_window_days` int default 14
- `returnability_source` text — `ai | manual` (AI авто-сорт, адмін перевизначає)

**`orders` (розширення):**
- `received_at` timestamptz — фактичне отримання (з трекінгу НП)
- `tracking_status` text — останній статус доставки НП

**Сторейдж:** приватний бакет `payment-receipts` + RLS на `storage.objects` (читання/запис лише через сервісну роль edge-функцій).

GRANT-и зберігаються наявні; нові колонки успадковують доступ існуючих таблиць.

## Частина 2 — Автоматизація (Edge Functions + Cron)

**`process-payout` (розширення наявної):**
- `split_order` — при створенні замовлення проставляє `payout_stage='created'`, `payout_type`, рахує суми (вже частково є).
- Нова дія `recalc_eligibility` — для отриманих замовлень рахує `eligible_payout_at` = `received_at` + (`is_returnable ? max(return_window_days) : 0`).
- Нова дія `run_auto_payouts` — бере splits зі `created`, де `eligible_payout_at <= now()`, переводить у `processing`, виконує перерахування на реквізити постачальника (`payment_iban/card_holder/bank_name`), створює запис у `supplier_payouts`, генерує авто-чек і ставить `paid` + `paid_at`.

**`track-deliveries` (нова):** періодично через наявну `nova-poshta` (action `trackPackage`) перевіряє ТТН активних замовлень; коли статус = «отримано», проставляє `orders.received_at`, `tracking_status`, далі викликає `recalc_eligibility`.

**`ai-returnability` (нова):** через Lovable AI класифікує товар за категорією (білизна, їжа, гігієна → незворотні; решта → 14 днів), проставляє `products.is_returnable/return_window_days/returnability_source='ai'`. Запускається для нових товарів та пакетно.

**`manage-payments` (нова, сервісна роль):** єдина точка доступу для адмін/модератор перегляду й дій (за патерном `manage-user-roles`):
- `list` (фільтри: магазин, статус) — для адміна (усі) і модератора (перегляд).
- `mark_received` — ручна позначка отримання (резерв, якщо трекінг недоступний).
- `upload_receipt` / `mark_paid` — ручні дії адміна (резерв до авто-чека).
- Перевірка ролі через токен; модератору — лише read.

**Cron (pg_cron + pg_net, через insert-tool):** `track-deliveries` кожні 30 хв; `run_auto_payouts` раз на годину.

## Частина 3 — Інтерфейс

**Адмін — нова вкладка «Керування оплатами»** (`AdminDashboard.tsx` + новий `PaymentsManager.tsx`):
- Фільтри: магазин, статус (Створено / В обробці / Оплачено), пошук за № замовлення.
- Картки виплат із сумами (роздріб / дроп / націнка), типом оплати, таймером `eligible_payout_at`, кнопками «Позначити отримано», «Завантажити чек», «Виплатити».
- Перегляд/прикріплення чека до кожного куска.

**Модератор — нова вкладка «Оплати»** (`ModeratorPanel.tsx`): той самий список згрупований по магазинах, лише перегляд статусів + резервна позначка «отримано» (за відповіддю користувача — основне джерело трекінг НП).

**Постачальник — статуси у «Замовлення»** (`SupplierOrders.tsx` / `StoreManagement.tsx`): для кожного замовлення бейдж оплати (Створено / В обробці / Оплачено), сума до виплати та посилання на чек, коли оплачено.

## Технічні деталі

- Доступ адмін/модератор до фінансів — лише через `manage-payments` (PII/фінанси не читаються напряму з клієнта; відповідає memory про safe-доступ).
- Перерахування поки фіксує запис у `supplier_payouts` зі статусом і авто-чеком (інтеграція реального банк-API ФОП — окремий крок; гачок уже передбачено в `process-payout`).
- Зворотність товару впливає на `eligible_payout_at`: незворотний → виплата одразу після отримання; зворотний → +14 днів.
- Реквізити постачальника вже існують у `suppliers`/`supplier_applications` (`payment_iban`, `payment_card_holder`, `payment_bank_name`) — додаткових полів не треба.

## Порядок робіт

1. Міграція БД + бакет `payment-receipts` + RLS.
2. Edge-функції: розширення `process-payout`, нові `track-deliveries`, `ai-returnability`, `manage-payments`.
3. Cron-джоби.
4. UI: `PaymentsManager` (адмін), вкладка модератора, бейджі постачальника.
5. Перевірка: тест edge-функцій, тест-ролі через перемикач (жук) бачать панелі автоматично.
